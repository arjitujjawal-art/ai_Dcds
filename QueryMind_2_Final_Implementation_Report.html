2. Voice Input & Audio Signal Processing Implementation

Voice functionality is implemented in static/js/voice_sql.js and styled in static/css/style.css:

  • Client-Side Speech Recognition: Built on the W3C window.SpeechRecognition / window.webkitSpeechRecognition API. Captures microphone audio in real-time with continuous transcription.
  • Live Audio Waveform Animation: Uses the Web Audio API (AudioContext) to animate a pulsating multi-bar audio wave (#listeningWave) during active recording.
  • Microphone State Machine: Handles permission states (ready, listening, denied, error) with visual status indicators (#micStatusDot).
  • Spoken Word Normalization (nlp/sql_generator.py): Implemented normalize_spoken_numbers() to translate verbal number words into numeric tokens (e.g., "top five students" → "top 5 students", "attendance below seventy five percent" → "attendance below 75%").
  • Pre-Execution Safety Guarantee: Microphone speech strictly populates the query textarea (#voiceQuestionInput). Queries are never auto-executed on speech stop. Users inspect the generated SQL and click [Run Query].

3.1 Implementation of explain_query_plan()

Implemented in db/database.py and app.py: 

def explain_query_plan(sql: str) -> dict:
    # Executes EXPLAIN QUERY PLAN and introspects optimizer execution steps
    conn = _conn()
    c = conn.cursor()
    c.execute(f"EXPLAIN QUERY PLAN {sql}")
    raw_rows = c.fetchall()
    conn.close()

    plan_steps = []
    has_index_scan = False
    has_temp_btree = False

    for r in raw_rows:
        detail = r[3] if len(r) > 3 else str(r)
        step_type = "FULL_TABLE_SCAN"
        if "SEARCH" in detail.upper():
            step_type = "INDEX_SEARCH"
            has_index_scan = True
        elif "USE TEMP B-TREE" in detail.upper():
            step_type = "TEMP_BTREE_SORT"
            has_temp_btree = True

        plan_steps.append({"id": r[0], "step_type": step_type, "detail": detail})

    return {
        "status": "success",
        "steps": plan_steps,
        "summary": {
            "step_count": len(plan_steps),
            "has_index_scan": has_index_scan,
            "has_temp_btree": has_temp_btree,
            "optimization_level": "High (Indexed)" if has_index_scan and not has_temp_btree
                                  else ("Moderate (Sorted with B-Tree)" if has_temp_btree else "Sequential (Full Scan)")
        }
    }

3.2 Live Verified Optimizer Benchmark

When running the query: SELECT s.name, m.marks FROM students s JOIN marks m ON s.student_id = m.student_id ORDER BY m.marks DESC LIMIT 5, the live endpoint returns:

  • Step 1: SCAN m → FULL_TABLE_SCAN on table marks.
  • Step 2: SEARCH s USING INTEGER PRIMARY KEY (rowid=?) → Index-accelerated INDEX_SEARCH on table students.
  • Step 3: USE TEMP B-TREE FOR ORDER BY → TEMP_BTREE_SORT allocated for descending order ranking.
  • Optimization Level: Evaluated as Moderate (Sorted with B-Tree) with 2 tables accessed.

4. Supabase PostgreSQL 15+ Migration & Dual-Engine Adapter

The database architecture bridges local zero-config operation with production cloud PostgreSQL:

  • Dual-Engine Database Adapter (db/supabase_adapter.py): Detects SUPABASE_URL and SUPABASE_KEY / DATABASE_URL. Routes queries to cloud PostgreSQL with connection pooling when configured, and falls back to local SQLite (db/querymind.db) with zero external setup.
  • PostgreSQL 15+ Schema Migration (migrations/001_initial_supabase_postgres_schema.sql): Complete DDL with Primary Keys, Foreign Keys with ON DELETE CASCADE, composite unique constraints on (student_id, subject_id, exam_type), and generated stored columns.
  • Row-Level Security (RLS) Policies: Enforced at the database kernel level: 
    ALTER TABLE public.students ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.marks ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Student read own profile" ON public.students FOR SELECT
  USING (auth.uid() IN (SELECT auth_uid FROM public.users WHERE users.user_id = students.user_id)
         OR EXISTS (SELECT 1 FROM public.users WHERE auth_uid = auth.uid() AND role IN ('faculty', 'admin')));
  • Data Migration Script (scripts/migrate_sqlite_to_supabase.py): Reads records from local SQLite and generates transactional SQL (migrations/002_data_seed_supabase.sql, 257 lines) with sequence synchronization (setval).

8. Academic Viva Defense & Curriculum Presentation Guide

When presenting QueryMind 2.0 to academic evaluators or defense committees, emphasize the following core architectural distinctions:

  1. Relational DBMS Foundation: QueryMind is not a superficial AI wrapper. It exposes relational database internals: foreign key constraints, 3NF normalization, composite indexes, B-tree sort buffers, and SQL execution trees.
  2. Voice as Input, Not Output: The microphone is strictly an input capture mechanism. Spoken natural language is converted to text and translated to SQL for pre-execution inspection. The user retains authoritative control before any query runs.
  3. Deterministic AST Governance: Queries are validated using SQLGlot AST parsing rather than brittle string matching. DDL/DML injection attacks are neutralized mathematically at the abstract syntax tree level.
  4. Dual-Engine Architecture: The application supports cloud Supabase PostgreSQL 15+ with kernel-level Row-Level Security (RLS) while providing an instant, zero-config SQLite fallback for local development and CI testing.
  5. Query Execution Profiling: The [Explain Plan] drawer demonstrates real-world query optimization, allowing students to observe how indexes convert full table scans into fast B-tree searches.
